# 解析报告面板（上传页结果阶段）

## 要解决的问题

解析完成后，用户看到的应该是"这批资料到底处理成什么样了"，而不是被直接推进预览页。
原来的结果卡只有三个数字（模块 / 知识点 / 考点标注）和三个跳转按钮——
不足以解释这次解析发生了什么，尤其是**花了多少 token**。

## 交互

解析完成 → 隐藏进度浮层与上传卡片 → 显示结果卡（**不自动跳转**）→ 用户点「查看资料导览」
或「打开思维导图」才离开。第三个按钮「再处理一批」清空回到上传态。

结果卡分两层：

1. **顶部三数字**：模块 / 知识点 / 考点标注。由前端拿 `/api/result` 的树**现算**
   （`KT.bookModules` / `KT.moduleStats`），所以即使报告接口挂了也能显示。
2. **下方数据面板**：补上树里没有的信息 —— 四个分区
   - **AI 增强**：覆盖率、已有摘要节点数、导学覆盖、模型、增强范围（层级/上限）、成功与兜底
   - **LLM Token 消耗**：合计 / 输入 / 输出 / 调用次数 / 其中思考
   - **文件**：文件数（PDF / Word / TXT 构成）、PDF 总页数、总耗时
   - **结构审校**：修正顺序多少组、AI 参与多少组、坏标题待修 → 剩余
   - **章节边界**：补回标题数（列出补回的标题）、自动分隔的未识别边界数、待确认提示
     （来自 `outline_skeleton` 的解析/增强前置报告；无任何问题时该分区不显示）

## 统计口径（重要）

**token 只统计 AI 增强阶段**，即 `server._enhance_tree` 内部的三段：
结构审校（`structure_repair`）+ 节点增强（`enhance_book_nodes`）+ 导学生成（`generate_guides`）。

不计入的有：MinerU OCR、无结构文本的 LLM 结构化（`llm_structurer`）、建树期的层级校验
（`tree_builder.validate_and_repair_hierarchy`）。原因：它们都发生在增强阶段之前，
且 MinerU 本身不返回 token —— 它按页计费，所以面板给的是**页数**而不是 token。

面板上写明了这句口径（"只统计 AI 增强阶段…OCR 与文本提取由云端按页计费"），
避免把 4981 这个数字误解成"这次解析的全部花费"。

## 实现

| 位置 | 作用 |
|---|---|
| `parse_report.py` | `UsageMeter`（协程/线程安全的 token 累计器）、`tree_stats()`、`count_guides()`、`build_report()`、`summarize_for_message()` |
| `node_enhancer.py` | `enhance_book_nodes` / `enhance_one` / `generate_guides` / `generate_module_guide` 各加 `usage=None`，仅在 HTTP 200 时 `usage.from_response(resp, model)` |
| `structure_repair.py` | `audit_book_tree` / `audit_groups_with_llm` / `audit_group_with_llm` 同样加 `usage=None` 并逐层透传 |
| `server.py` | `_enhance_tree` 建 meter 并挂到 `task.token_usage`；`on_progress` 捕获增强 stats 存 `task.ai_meta`；审校报告存 `task.audit_meta`；`run_pipeline` 统计文件数/PDF 页数（fitz）/耗时，组装后落盘 `data/_temp_uploads/{id}/report.json` |
| `GET /api/report/{task_id}` | 内存活任务 → 磁盘 `report.json` → 从树现算的降级版（带 `partial: true`） |
| `outline_skeleton.py` | 结构前置层：大纲标题恢复 / 骨架校验 / 占位修复；报告随 `task.skeleton_meta` 汇总 |
| `ui/upload_mindmap.html` | `loadResult()` 追加拉取报告，`renderReport()` 渲染分区（含「章节边界」） |

### 三个必须遵守的口径对齐点

1. **模块数必须用 `book_modules()` 解包**，与前端 `KT.bookModules` 同一规则。
   真实数据里 4 棵树有 3 棵是「AnythingMindmap → 单本书 → 17 章」的单册包装结构，
   后端若按原始 `children` 数会显示"模块 1"，与页面上的 17 直接矛盾。
2. **节点总数含根节点**，与前端 `moduleStats(root)` 一致。
   外教树 1591 这个可对外引用的数字就是这么来的，少算根节点会变成 1590。
3. **`UsageMeter` 必须显式传递实例**，不能用模块级全局 —— 两个上传任务可能同时跑。
   累计过程加锁，因为增强阶段是并发调用（8 线程 × 250 次压测无丢数）。

## 已知问题：导学挂在包装节点上

`generate_guides` 遍历的是 `tree['children']`，而单册包装结构下这里只有一个包装节点
（如「外教」）。实测（真实 API 调用）结果：

```
根节点 guide      : True
包装节点 '外教'    : True      ← 导学落在这里
  模块 '第一章'    : False     ← 17 个真模块一个都没有
  模块 '第二章'    : False
  模块 '第三章'    : False
```

前端 `bookModules()` 解包后拿到的是那 17 个模块，它们 `guide` 为空 → **导学块与学习路径
在页面上是空的**，且重跑管线不会改善（因为问题在挂载层级，不在有没有跑）。

`count_guides()` 用 `wrapper_guide` 字段把这个信号暴露出来，面板上会显示
"导学覆盖 0 / 17"。修复方向是让 `generate_guides` 也走 `book_modules()` 解包；
**尚未修改**，因为会改变增强产出的结构，需先确认。
