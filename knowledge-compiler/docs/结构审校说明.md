# 结构审校：在 AI 增强环节内修正顺序与标题

## 为什么要做

解析（OCR → markdown → 建树）留下的缺陷会一路带到最终知识树，用户打开思维导图
直接看到「（一）三、二」这样的乱序节点。实测四本教材（4236 节点）：

| 问题类型 | 实测数量 | 说明 |
|---|---|---|
| 顺序矛盾 | 231 组 | 兄弟节点编号与渲染顺序不一致（一、三、二） |
| 编号重复 | 73 组 | 同一父节点下编号出现重复值，常见于「该下沉的子列表被拍平」 |
| 编号断档 | 20 组 | 编号缺号，通常是 OCR 丢了标题行 |
| 坏标题 | 69 个 | 只剩编号、标题文字被拆走（`知识点四`、`1. 学`） |

约定：**只在增强环节里修，不动原有解析/建树逻辑**；允许排序与一定程度的重命名
（仅当原标题本身不良时）；LLM 直接输出新结构，但代码负责校验与执行。

> 2026-10-15 起：审校**已固化进增强环节，不再对用户开放开关**。
> 原设置页的「结构审校」卡片已移除，`app_settings.audit_config()` 恒返回
> `{"enable_llm": True}`，`server._enhance_tree` 无条件调用 `audit_book_tree`。
> 旧 `data/settings.json` 里存的 `audit.enable_llm=false` 不再生效。
> 无 API key 时仍会自动退化为仅确定性审校（顺序类问题照修）。

## 架构

```
server._enhance_tree
  ├─ 健康检查
  ├─ ★ structure_repair.audit_book_tree(tree, chat)     ← 本层
  │     ① collect_audit_groups(tree)   在「原样」树上收疑点组（必须在修正之前）
  │     ② deterministic_audit(tree)    按编号把可证的顺序错乱全部修掉
  │     ③ audit_groups_with_llm(...)   LLM 兜底：编号重复/断档、坏标题
  │     ④ stamp_seq(tree)              写下最终序 seq_index
  ├─ tree_fingerprint(tree)            ★ 必须在审校之后取（见「坑」）
  ├─ enhance_book_nodes                （原有，逐节点摘要/关键词/考点）
  ├─ generate_guides                   （原有，章/全书导学）
  └─ cleanup_tree_structure            （原有，末轮结构整理）
```

新增文件 `structure_repair.py`。`node_enhancer._normalize_children_order` 重写
（原实现是乱序元凶）。`tree_builder` 给节点加 `src_index` 源序。

## 三层分工

**1. 确定性层（始终生效，不花调用）**
`（一）（三）（二）` 这类只要读编号就能判定对错的问题，不麻烦模型。1811 个可增强
节点里，顺序类问题 231 组全部在这层清零。

**2. LLM 层（只处理疑点）**
只有「编号重复 / 编号断档 / 坏标题」才送模型。纯顺序乱不送——确定性已经能修，
让模型再动反而可能改错。LLM 用**索引**而非标题回传：

```json
{"order": [0, 3, 1, 2], "renames": {"2": "知识点四 希腊化时期的教育"}}
```

**3. 护栏层（代码强制执行）**

- `order` 必须是 `0..n-1` 的一个合法排列，否则整组丢弃、本组不发生任何变化
- 绝不增删节点；节点数与标题多重集逐本校验，实测 4236 → 4236 完全守恒
- **只改「坏标题」**：`bad_title_reason()` 判定为 markdown 残留 / 纯编号 /
  OCR 噪声 / 异常超长 才允许改。正常标题不送模型、模型也改不动
- **改名不得丢编号前缀**：`知识点四` → `希腊化时期的教育` 会被拒绝
  （会掉出编号族、制造新断档）；`知识点四` → `知识点四 希腊化时期的教育` 通过
- 不许与兄弟节点重名（否则触发去重逻辑反而删节点）

## 为什么有些坏标题改不动

69 个坏标题全部是 OCR 把标题拆成两行所致：`# 知识点四` 与真正的标题
`# 希腊化时期的教育` 各占一行，后者被 `hierarchy_repair` 嵌成了前者的子节点。
这类**不是改名能解决的**，需要合并节点——那会减少节点数，超出本次约定范围。
目前给出材料让模型补全（prompt 里附第一个子标题），并强制保留编号前缀。

## 踩过的坑（已修，写下来避免重蹈）

1. **`_normalize_children_order` 是乱序元凶**：原实现从 title 现抓正则，匹配不上
   就按 Unicode 码点排到队尾。中文编号 `一、二、三` 匹配不上 `\d+`，于是
   `（一）（三）（二）` 恰好是码点序。已改为优先读 `number_path`/`raw_prefix`，
   无编号时按 `src_index` 恢复文档序，两者都没有才保持原序。
2. **`_cn_num_to_int` 算错中文数字**：`第二十章→30`、`一十二→10`、`第一百章→1`。
   已改调 `hierarchy_repair.chinese_to_int`（权威实现）。
3. **`str.isdigit()` 对 `①` 也返回 True**：圆圈数字必须先判，否则 `int("①")` 抛异常。
4. **重排必须写回父节点 children**：`collect_audit_groups` 若只存一份成员副本，
   LLM 的重排只会改到临时列表上被静默丢弃，改名还会落到已经错位的下标上。
   已改为 `_Group` 持有槽位索引，`apply_order()` 按槽位写回。（这是验证阶段发现
   的最严重缺陷，一度使 LLM 重排整块失效。）
5. **`asyncio.run()` 在已运行的事件循环里会抛异常**：`_enhance_tree` 本身是 async，
   审校必须 await 而不是 `asyncio.run`。
6. **断点续跑指纹必须在审校之后取**：指纹基于 `title|depth`，审校会改标题，
   先取指纹会把结果挂到「修好之前」那份指纹上，续跑失联。
7. **`int(float('inf'))` 抛 OverflowError 而非 ValueError**：畸形 JSON 一度能把
   整个审校阶段打挂，已并入异常处理。
8. **审校结论会被末轮 `cleanup_tree_structure` 冲掉**：无编号组的兜底是按源序
   排序，LLM 的调整会被回退。已写 `seq_index` 记录最终序供下游沿用，
   且**不动 `src_index`**——原文序始终可追溯、可纠错。

## 取舍

- **保守优先**：判不准就别动。宁可留下 69 个坏标题，也不编造标题曲解原文。
- **顺序用编号优先于源序**：文档自己的编号就是它的排序声明，源序只在无编号时
  作为兜底（此时 `src_index` 是唯一依据）。
- **混合编号族互不干扰**：同父节点下 `（一）` 与 `1.` 各自成组、只在组内重排，
  不交叉搬运位置。

## 速度基线

历史速度基线与 benchmark 脚本已移入本地归档区，不随 GitHub 仓库发布。历史规模账
显示：可增强 1811 个节点，而旧版服务端单次只取前 30 个，覆盖差约 60 倍。该数据仅作
背景记录；当前增强范围由设置页档位控制。
